# 开发规范

[返回开发者指南](readme.md)

日常改动由 subagent 在独立 worktree 中实现，完成后合入 `dev`。`dev` 积累一批已验收的改动后，再合入 `main`，在同一次发布流程中完成版本更新、部署和更新公告。

## 分支职责

| 分支     | 用途                                                                                   |
| -------- | -------------------------------------------------------------------------------------- |
| `dev`    | 日常开发的集成分支，汇总已完成的功能、修复、测试和文档；尚未正式发布的改动在这里积累。 |
| `main`   | 正式发布分支，合入一批改动时同步准备新版本与更新公告，生产部署使用该分支确认过的提交。 |
| 任务分支 | 从最新 `dev` 创建，一项独立任务对应一个分支和 worktree，完成后合回 `dev`。             |

初次建立 `dev` 时，从当时的 `main` 创建。分支操作、集成和发布都使用对应分支的干净 worktree，已有未提交改动先独立处理，避免混入其他任务。

## 实现与集成

1. 用户提出改动后，主 agent 明确任务范围与验收方式，再交给 subagent。多个独立任务各用自己的分支和 worktree。
2. subagent 从最新 `dev` 开始实现，补充适用的持久化回归测试和开发文档。跨测试套件复用的辅助代码放在 `tests/lib/`，套件内部辅助代码留在各自目录。
3. subagent 按[开发验证](testing.md)运行检查，交付 diff、验证结果及尚未解决的问题。代码改动执行 `pnpm check`，涉及界面、接口或协作运行时的改动再执行对应测试；纯文档改动检查格式和链接。
4. 主 agent 审阅结果、处理集成冲突并确认验收完成，再将任务分支合入 `dev`。用户要求先看 diff 时，先保留未提交改动供审阅；提交、推送和部署分别遵循用户本次授权。
5. 多个任务依次合入；集成产生代码变化时，补做受影响的验证。确认提交已保存在 `dev`、worktree 没有待保留内容后，再清理任务 worktree 和分支。

合入 `dev` 表示改动进入下一批候选发布，不为每个任务单独发布版本或向用户弹出公告。发布时机和范围由用户决定，不以提交数量自动触发。

## 批量发布

发布以用户确认的一批 `dev` 改动为范围，按以下顺序完成：

1. 在 `dev` 汇总自上次发布以来的改动，确认验收结果、待解决问题和迁移影响；未完成的任务继续留在任务分支。
2. 在 `dev` 准备发布提交：更新根目录 `package.json` 的版本号，在 [releases.ts](../../src/data/releases.ts) 添加与该版本一致的公告，并整理 GitHub Release 说明。公告写用户可感知的变化和必要操作，字段规则见[发布新公告](releases.md#发布新公告)。
3. 在待发布提交上执行 `pnpm check` 和本批改动对应的运行验证。确认后将 `dev` 合入 `main`，保留分支合并关系；若处理冲突改变了代码，重新验证受影响的内容。
4. 推送经确认的分支，从 `main` 的发布提交按[部署说明](../deployment.md)部署，核对实际运行版本，并验证首页、登录、主要改动及更新公告。Cloudflare 部署使用 `pnpm run deploy`；普通 Git 合并不会自动执行部署。
5. 部署验收通过后，在同一发布提交创建 `v<版本号>` tag、推送 tag 并发布 GitHub Release。根目录版本号、应用内公告、tag 和 GitHub Release 使用同一版本号。部署或验收失败时，先修复并重新验证，再完成发布。
6. 将 `main` 合回 `dev`，确保下一批开发包含正式发布的全部提交；收尾修复同样需要回到 `dev`，避免下次发布遗漏。

应用内更新公告随前端产物一起部署，已打开的旧页面不会主动接收新公告；用户重新打开或刷新后，按账号在当前浏览器中的展示进度决定是否弹出。具体行为见[更新公告与更新日志](releases.md)。
